# 开发笔记

旁白助手的设计、处理流程、实测数据和踩过的坑，给想改代码的人看。功能介绍、使用和编译见 [README](../README.md)。

## 原理

iOS 16 起，App 可以通过 `AVSpeechSynthesisProviderAudioUnit` 扩展向系统提供“第三方声音”，旁白、朗读屏幕都能选用。

本项目的扩展不自带引擎，而是**在扩展进程里调用系统的 `AVSpeechSynthesizer.write()`**，拿到苹果声音的 PCM 再处理：

```
旁白发来 SSML（文字 + 语速/音调/音量 + 停顿/句子）+ 所选方案
  → 改写 SSML（ApplePlanner）：
      语速原样交给苹果声音（旁白发来的就是实际倍数，最快约 4 倍）；
      文字过朗读修正规则，再按方案的数字读法转换数字；另一种语言包进 <voice name="副语音">（苹果自己切换声音；
      副语音和主语音一样先换成系统里实际有的声音，没有就用这种语言的默认声音，这种语言一个都没有就不用副语音）；
      去掉旁白的 xml:lang / <lang> / <voice>（声音由方案决定）；停顿、句子等结构原样保留
  → 苹果声音一次读完整个 SSML（停顿按语速缩放，和原生一样）
  → 去掉整句前后的空白（以 <break> 开头/结尾时保留）；换声音处没有标点时，两个声音保留自然的收尾和起音，
    中间不再另加停顿（不做成设置）；有标点时保留苹果自己的停顿；句中停顿原样保留、不做淡入淡出（以前每个
    4 ms 以上的安静处前后都淡了 3 ms，会削弱塞音的爆破，如“播客”的 b、k；只有被剪短的停顿才需要）
  → 副语音的段落按需做音量平衡
  → 变速 = 方案的语速加倍：Sonic（C 原版，NVDA 同一版本），不变调
  → 一段声音一结束就整段放出（不等下一个声音开口）
  → 交给系统播放（AudioRing：手里够宿主拉一整块就开始，宿主实测每次拉 256 帧约 12 ms；换声音还没完成时要有 300 ms 才开始，否则等新声音真正出声——它产出满一块之后才算换完）
```

**语速分工：** 旁白的语速滑块（或转子）只管苹果声音本身的快慢，和旁白直接用这个声音完全一样；方案里的“语速加倍”只能在 App 里设，全部由 Sonic 完成。嫌苹果声音高速时吃字，可以把旁白语速调低、把加倍调高（NVDA 的做法就是引擎保持正常语速、全部交给 Sonic），自己选最清楚的组合。

**加速算法：** Sonic（Bill Cox，Apache 2.0）是专为盲人高倍速听读做的变速算法，NVDA 的“语速加倍”用的就是它。`Sources/CSonic` 是 NVDA 锁定的那次提交（b93885d）的原版 C 代码，未作修改，按 NVDA 的方式调用（16 位整数、默认质量）。早期用过的 WSOLA 在 2.5 倍以上会失真（Sonic 作者的结论），已删除。也试过 Google 的非线性加速 Speedy，没有采用。

**停顿：** 苹果声音读 SSML 时会按语速缩短停顿（实测 500 ms 的 `<break>`：正常语速 459 ms，最快 108 ms），所以把旁白的 SSML 原样交给它，停顿就和原生一样。自己插静音（早期的做法）在高语速下会长出几倍。停顿和语音一起经过 Sonic，所以也按方案的加倍缩短；整句前后的静音一律去掉（以 `<break>` 开头/结尾时保留）。早期版本里这两项是全局开关，现在固定打开，settings.json 里旧的开关值不再读取。

旁白 SSML 里的语速就是实际倍数（iPhone Air、iOS 27 上抓日志实测）：50% 发 `100%`，每加 5% 多 30%，55% 发 `130%`，100% 发 `400%`。苹果声音读 SSML 用的是同一个刻度（`X%` = X/100 倍，最快约 4 倍），所以原样传过去。旁白直接用苹果声音时的速度（App 用 `prefersAssistiveTechnologySettings` 实测）和这些值相差不到 5%，只是原生有几处不均匀（90% 和 95% 一样快，40% 和 45% 一样快），这些不照搬。早期版本把它当成“相对默认语速 0.5”，再套苹果 `rate` 那条很陡的曲线：55% 读成 1.8 倍，70% 以上全是 4 倍。50% 以下旁白发什么还没抓到，App 试听时按 0% = 0.5 倍均匀推算。

副语音的“相对语速”按实测的 `rate`→实际倍速曲线换算（Mac 和 iOS 一致：0.5=1 倍，0.6≈1.6 倍，0.7≈2.1 倍，0.8≈2.8 倍，1.0≈4 倍），App 首次启动时在手机上再测一遍。

只会使用苹果自己的声音（标识以 `com.apple.` 开头），绝不会用第三方声音——否则可能调回自己，形成递归。

## 语音方案

每个方案有固定的内部编号（系统里的声音标识 `com.zdyi.voassist.s.<UUID>`），改名、调参数旁白不用重选；主语音换了语言，方案会移到别的语言列表，需要在旁白里重选。方案的 `id` 和默认方案的 UUID 不能变，新加的字段一律用 `decodeIfPresent` 解码，读不懂的值（比如以后版本加的数字读法）退回默认值，不让整个方案作废。

默认方案只有一个“婷婷+Samantha”（婷婷读中文、Samantha 读英文），编号固定（`5A1C0000-…-000000000001`），App 第一次运行前扩展就先提供它。早期还有“Samantha”“善怡”两个默认方案（编号 …002、…003 不再使用），已经装过的手机上它们作为普通方案保留。

副语音音量平衡默认打开，App 测好两个声音的响度之前不调。早期版本默认关，那时存下的方案在 App 第一次打开新版时统一打开一次（`balanceVolumeOnByDefault`），之后关掉就一直关。

粤语声音的语言代码是 `yue-HK`（标识里却是 `zh-HK`），代码里“中文”统一指 `zh-*` 和 `yue-*`。

## 中英分段规则

副语音只读单词，数字和符号一律归主语音（试过交给英文声音：电话号码、`MP3` 的 3 用英文读，`Node.js` 的点、`user@example.com` 的 @ 被英文声音读出或吞掉，都不对）。

- 中文主语音：连续的英文字母（带重音的也算，`café`、`Pokémon`、`Zürich` 不会被拆开）交给副语音，单词中间不发音的撇号、连字符（`don't`、`Wi-Fi`）和单词之间的空格算在单词里。数字（`MP3` 的 3、`Tel13800138000` 的号码）和符号（`@ # / & + = _` 等）都由主语音读，主语音单独拿到一个符号时读它的名字（实测婷婷：`.` 读“点”，`@` 读“at”）：`Node.js` → Node / 点 / js，`user@example.com` → user / at / example / 点 / com，`https://` → https / “://” / …（网址会在两个声音间来回切，可以接受）。
- 其他主语音（日语除外，日文汉字也是汉字）：连续的汉字（带中文标点）交给中文副语音，数字归主语音（`2026年` → 2026 / 年）。
- 换声音处如果是旁白自己要求的停顿（`<break>`，或 `<s>` 分句、`<p>` 分段，比如“App Store”和提示“轻点两下以打开”之间的 800 ms），保留苹果做出的整段停顿，不压缩；以前会被当成中英连读压成 0，提示紧贴着英文名称冒出来。实测这段停顿在上一个声音那段的结尾（App Store 那段末尾 656 ms），比同样位置的中文多出约 110 ms（换声音时苹果额外给的结尾空白），没再削。
- 拆分后某一段只剩一个大写字母（“学 C 语言”的 C）时转成小写：苹果声音单独读一个大写字母会加“capital”/“大写”（实测 Samantha、婷婷都会），在上下文里或小写时只读字母。整句只有这一个字母（旁白按字符移动）时不动，那是旁白原生的读法。
- 全角数字、全角字母（`Windows１０`）按普通数字、字母处理，不当作中文标点并到英文那段。
- 只表示停顿的标点（句号、逗号、问号、冒号、引号、括号等，即 NVDA Dual Voice 插件说的 complex 标点）不读出来，并到前一段，换声音处的停顿由前一段末尾的标点决定。例外：夹在两个英文单词中间的点（`example.com`）读作“点”；后面紧跟符号的标点（`https:` 的冒号）随符号一起归主语音。
- 参考过：NVDA Dual Voice（标点当空格，符号和数字可选归拉丁声音、非拉丁声音或跟随上下文）、WorldVoice（标点跟随上下文，另有用户符号表可强制某符号用某语言读）、NVDA 中文符号表（读法参考，GPL，未复制）。

## 数字读法

方案里分三档。数字一律由主语音读，所以按主语音的语言转换。先执行修正规则（这样规则还能匹配到阿拉伯数字），再转换数字（`Numbers`）。

- **默认**：完全交给系统声音，不改。婷婷实测：`1234` 读“一千二百三十四”，`2024年` 读“二零二四年”，`12:30` 读“十二点三十分”，`50%` 读“百分之五十”，`-5` 读“负五”。
- **数值**：先把数字写成汉字或英文单词，再交给声音读。
  - 中文：`1234` → 一千两百三十四，`2024年` → 两千零二十四年，`3.14` → 三点一四，`50%` → 百分之五十，`-5` → 负五，`1,234,567` → 一百二十三万四千五百六十七，`MP3` → MP 三。
  - “两”用在三种地方：百、千前面的 2；万、亿前面那一组只有一个 2 时（两万，但十二万）；单独一个 2 后面跟量词时（`2个` → 两个）。`第2个`、`2年级`、`2月` 仍读“二”。
  - 英文：`1234` → one thousand two hundred thirty-four，`50%` → fifty percent，`-5` → minus five，`MP3` → MP three。
  - 不转换（系统声音本来就按数值读）：用 `- / : ~` 连起来的数字组，即时间 `12:30`、日期 `2024-10-17`、电话 `138-0013-8000`、分数 `1/2`、范围 `1~2`；还有英文序数（`1st`）。
  - 逐位读：以 0 开头的（`007`、`0571`），中文超过 16 位、英文超过 15 位的，以及小数点后面的部分。
  - `192.168.1.1` 这种多个点连起来的，每段按数值读，中间读“点”。
- **数字**：逐位读，时间、日期、电话也逐位读。中文：`1234` → 一二三四，`2024年` → 二零二四年，`3.14` → 三点一四，`50%` → 百分之五零，`12:30` → 一二:三零，`1,234` → 一二三四。英文：one two three four。
- 繁体中文和粤语主语音用繁体字：兩、萬、億、點、負。
- 其他语言：“数字”档在数字之间加空格（`1 2 3 4`）；“数值”档和默认一样交给系统声音。
- 全角数字和全角百分号（`１０％`）按普通的数字和百分号处理。

## 朗读修正规则

每条规则：查找、替换为、是否正则、是否忽略大小写、是否只匹配完整英文单词、备注、开关。按列表顺序依次执行，每条作用在上一条的结果上。写错的正则会在 App 里标红，朗读时跳过。正则没有超时限制，写出灾难性回溯的正则会卡住合成。

## 分享格式

```json
{
  "format": "voassist",
  "version": 1,
  "schemes": [ { "name": "婷婷", "main": {"id": "com.apple.voice.super-compact.zh-CN.Tingting", "name": "婷婷", "lang": "zh-CN"},
                 "secondary": {"id": "com.apple.voice.super-compact.en-US.Samantha", "name": "Samantha", "lang": "en-US"},
                 "boost": 2, "numbers": "values" } ],
  "rules": [ {"find": "重新", "replace": "虫新"}, {"find": "(\\d+)%", "replace": "百分之$1", "regex": true} ]
}
```

只有 `format` 必须有，其余省略的字段取默认值；读不出来的单个方案或规则跳过，不影响其他的（App 自己的 schemes.json、rules.json 也一样，免得一条坏数据让下次保存把整个列表清掉）；副语音不是苹果声音的会被去掉。也接受只有规则的数组（最早的导出格式）。导入时方案一律作为新方案加入（同语言重名加“（2）”），和已有规则完全相同的规则跳过，对方手机上没有的声音会提示。`numbers` 是数字读法：`system`（默认）、`values`（数值）、`digits`（数字）。

## 诊断日志

App 主页“日志”分组：记录日志（开关，一小时后自动关闭）、记录朗读内容（开关，每次打开日志都会复位为关）、发送日志、清空日志。

- 开关存在共享的 settings.json（`logUntil`、`logSpeech`），扩展每次写之前都看一眼，开关立刻生效；关着时什么都不写。
- 扩展写不了 App Group，所以日志写在扩展自己的容器里（`Library/Application Support/Diagnostics/log.txt`，超过 1 MB 换成 `log.old.txt`，总共不超过约 2 MB）。实测扩展的各个进程（系统查声音列表时拉起的、旁白用的、App 加载的）共用这个容器，iPhone 和 Mac（TestFlight 装的 iPhone 版）上都验证过。每个进程在每个新文件里先写一行自己是什么（进程、版本、系统）；每行都带时间和进程号。
- App 取日志：加载一次扩展，往它的 `fullState` 写命令 `sendLog`，下一次读 `fullState` 就带上日志（`clearLog` 清空）。发送的文件开头是 App 这边的信息：手机型号、系统和 App 版本、旁白开没开、日志状态、规则条数、扩展可用的声音、语速曲线、方案。
- 记的内容：
  - 系统对扩展的每次调用（创建、释放、查声音列表、分配和释放资源、开始和取消朗读、读写状态），以及线程和耗时。锁屏、亮屏时系统是不是在等扩展，从这里能看出来。
  - 每句话：方案名，主副语音要的和实际用上的，旁白语速，加倍，数字读法，规则开没开，朗读的文字（只在打开“记录朗读内容”时记，最多 200 字，否则只记字数），等了多久才开始合成，多久出第一块声音，合成用时，怎么结束的，换声音用时。
  - 每句的播放：系统取了几次、每次多少帧，多久交出第一块声音，中途断流几次，有没有播完。
- 开发参数：`-logOn`（打开日志）、`-logSpeech`（同时记朗读内容）、`-clearLog`、`-printLog`（把要发送的全文打印出来）。

## 命令

```sh
swift test                                   # 单元测试（Mac）
swift run -c release render-samples --vo 50,100 --boosts 1,2,3 --out samples/x
                                             # 生成试听 WAV：旁白语速 × 方案加倍的各种组合（默认婷婷 + Samantha）
swift run -c release render-samples --voice com.apple.voice.compact.en-US.Samantha --text "Open 微信" --out samples/y
                                             # 其他方案：--secondary <声音标识|none>、--rules <分享文件>、--balance（音量平衡）、--numbers system|values|digits（数字读法）
                                             # --ssml '<speak>…</speak>'：直接给一个旁白式的请求
swift run -c release render-samples --cancel-test   # 打断测试：取消半句后立即读下一句
swift run -c release render-samples --text "Safari浏览器" --switch-delay 200 --out samples/z
                                             # 假装换声音要 200 ms（手机上可能这样），看实时播放会不会断
```

Mac 上没有内置版（`super-compact`）的婷婷时，用 `--voice com.apple.voice.compact.zh-CN.Tingting` 和 `--secondary com.apple.voice.compact.en-US.Samantha`。`samples/` 不进版本库。

### 真机调试

调试版（Debug）里多两样东西，正式版没有：主页最下面“调试 → 测量旁白语速”（按旁白当前语速读一句、计时，得出原生快几倍，记在 App Group 的 `Library/debug_native_rates.json`）；扩展把收到的每个请求写进系统日志（`VOASSIST-SSML`）。

```sh
xcodebuild -project VoAssist.xcodeproj -scheme VoAssist -configuration Debug -destination 'id=<UDID>' \
  -derivedDataPath build/dev-debug -allowProvisioningUpdates -allowProvisioningDeviceRegistration build
xcrun devicectl device install app --device <UDID> build/dev-debug/Build/Products/Debug-iphoneos/VoAssist.app
xcrun devicectl device process launch --console --terminate-existing --device <UDID> com.zdyi.voassist -- -autotest
xcrun devicectl device copy from --device <UDID> --domain-type appGroupDataContainer \
  --domain-identifier group.com.zdyi.voassist --source Library/debug_native_rates.json --destination x.json
sudo /usr/bin/log collect --device-udid <UDID> --last 15m --output vo.logarchive   # 要 root
/usr/bin/log show --archive vo.logarchive --predicate 'eventMessage CONTAINS "VOASSIST-SSML"'
```

手机锁屏时启动会失败（`Locked`）。刚装完时系统的组件列表里可能一时没有本扩展，但照样能加载，自检会照样去加载。

声音：`-- -listVoices` 打印 App 看到的中英文声音，以及扩展报上来的可用声音（`VOICE usable`）；调试版扩展在日志里记下每句请求的声音和实际用上的声音（`VOASSIST-VOICE`），加载时记下它看得到的声音（`VOASSIST-VOICES`）。

出声延迟：`xcrun devicectl device process launch --console --device <UDID> com.zdyi.voassist -- -latency` 让 App 像旁白那样驱动扩展、按实时节奏拉声音，打印每句从请求到第一个声音的毫秒数（不改任何设置）。分步计时：编译时加 `SWIFT_ACTIVE_COMPILATION_CONDITIONS=LATENCY_PROBE`，扩展会把每一步的时间写进日志（`LATENCY-TRACE`），正式版不含这些代码。

devicectl 只能读容器里的 Library、Documents、tmp。装调试版会替换手机上的 TestFlight 版，之后要从 TestFlight 重装。

## 实测记录

- 中英衔接：换声音处留约 20 ms 加余韵和新声音的整段起始静音，停顿明显；切掉两边低于 -40 dB 的收尾和起音、不留停顿，听起来很奇怪；把英文从婷婷整句朗读里剪掉、拼进 Samantha 的读音（SSML `<mark>` 定位）有咔哒声，放弃。现在：保留自然收尾和起音，中间不另加停顿（试过 15 ms，最后定为 0，不做成设置）。“轻点两下以打开Safari浏览器”（旁白 50%）换声音处低于 -40 dB 的空白：停顿 0 时 40/14 ms，30 时 70/44 ms，60 时 100/74 ms（可以用 `render-samples --switch-pause` 重新生成对比）。
- NVDA 的中英混读插件没有现成的衔接办法：WorldVoice 每种语言的片段由对应声音单独读完再读下一段；Dual Voice 用 SAPI5 的 `<voice>` 标签让引擎在句中换声音（和这里的做法一样）。
- 单元测试 80 个（Sonic / 静音裁剪 / 换声音时整段放出、换声音停顿 / 播放缓冲 / 旁白语速（实测格式）/ 软限幅 / SSML / SSML 改写 / 中英分段（含粤语）/ 修正规则 / 数字读法 / 方案编码 / 共享文件（重启后解锁前读不到）/ 诊断日志 / 播放统计 / 响度测量 / 分享导入合并）。
- 换声音：Mac 和 iOS 27 模拟器里一次换声音只要 1–15 ms，扩展进程里第一次（副语音还没加载）约 70 ms；iPhone Air 上 3–27 ms，副语音还没加载时第一次约 185 ms（`-autotest`）。用 `--switch-delay 200` 模拟慢的手机：“Safari浏览器”不再在 Safari 后断开，而是晚约 200 ms 开始、一口气读完；中英频繁切换的长句在高倍速下仍会在换声音处停顿（停在两段之间，不会切在词中间）。
- Mac 上端到端：旁白式请求（旁白 100%，含 500 ms 和 300 ms 停顿）与苹果原生朗读的句中停顿完全一致（112 / 68 / 68 ms）；婷婷、Samantha、善怡三种方案在旁白 50%/100% × 加倍 1–3 倍下时长符合预期；音量平衡测得 Samantha 比婷婷响 2.4 dB 并自动调低；打断测试 20/20。
- iOS 27 模拟器：扩展向系统提供的每个方案只声明自己的语言；扩展进程内整句 SSML 合成正常，预热后首音延迟 0–23 ms。
- 真机（iPhone Air、iOS 27）：扩展在旁白里调用系统声音正常；`-autotest` 扩展加载、婷婷合成、换声音都正常。数字读法三档在 Mac 上用婷婷、Samantha 合成核对过，真机旁白里还没听过。
- 真机（iPhone Air，调试版）：旁白每档发来的语速值（见“原理”），以及旁白原生每档的实际速度。
- 真机出声延迟（iPhone Air，`-latency` 测量，从请求到第一个声音）：中文短句 24–48 ms，其中苹果引擎出第一块声音占 12–28 ms，攒够开播门槛 6–10 ms，宿主拉取间隔 4–12 ms；中英混读 58–70 ms（多出的是等换声音）；扩展刚加载后的第一句 370–410 ms（加载声音）。据此把开播门槛 50 → 20 ms、换声音门槛 300 → 100 ms；之后为了更快，改成“够宿主拉一整块就开播”（第一块不会半截静音）。换声音门槛降到 100 ms 后“Safari浏览器”又出问题：Safari 声音够 100 ms 就开播，婷婷换上来后声音一点点到，Safari 放完就断，截尾巴、爆音、停一下才接“浏览器”；恢复 300 ms，并且新声音产出满一块才算换完（它的第一块可能很小），断流淡出淡入从 2 ms 加到 6 ms。真机旁白实测：每次拉 256 帧，焦点到出声 13–33 ms，其中苹果引擎 12–31 ms。
- 耗电：空闲时 CPU 为 0；静音裁剪和 Sonic 只占扩展 CPU 的约 1%，其余是苹果引擎（加倍越高越多）。试听播放完会停掉音频引擎、释放音频会话。

## 待确认

- 旁白 50% 以下发来的语速值。
- 已知问题：iOS 27 上中文短词发抖（如“播客”的“播”），iOS 26 正常，多台 iOS 27 手机都这样，判断是系统问题。Mac 上播放模拟没有断续。若以后确认和 Sonic 有关，可以考虑打开高质量（`sonicSetQuality(1)`，Sonic 耗电约 5 倍，但只占扩展的几个百分点）。
- 方案只声明一种语言后，旁白遇到英文内容是否仍交给方案（由副语音读），还是自己切到别的声音；后者的话需要关掉旁白的“检测语言”。
- `.voassist` 文件从微信“用其他应用打开”导入。
- 宿主对新一句的第一次拉取若早于新请求到达，可能拿到上一句十几毫秒的尾音（需要真机日志确认调用顺序）。

## 实现要点（踩过的坑）

- **语音扩展只能用系统内置的声音**（标识里是 `super-compact` 的，如婷婷、美嘉、善怡、Samantha、Daniel、Karen；iPhone Air、iOS 27 上抓内核日志实测）。扩展的沙盒拒绝读声音数据库（`deny file-read-data .../Accessibility/voicedb.sqlite`），也拒绝连资源下载服务、辅助功能声音服务和 Siri 语音服务（`deny mach-lookup com.apple.mobileassetd.v2`、`com.apple.accessibility.voices`、`com.apple.SiriTTSService.TrialProxy`），所以下载的精简/增强/高音质声音、Siri 声音、Eloquence 都拿不到；方案里选了这些，扩展会悄悄退回这种语言的内置声音，看起来就是“换了声音没变化”。App 自己看到的又和扩展不一样（下载了精简版婷婷后，App 里只有精简版，内置版查不到；Siri 声音 App 能用），所以由扩展把自己能用的声音放在 `AUAudioUnit.fullState` 里报给 App（`UsableVoices`），声音选择页只列这些；扩展还没报上来时先列 App 能看到的内置声音。App 里试听用的是 App 这边的声音，可能比旁白里实际读的好一点。早期的默认方案存的是精简版标识，扩展读出来就是同名的内置声音，听起来没区别，只是选择页里不打勾。
- **绕不过去（真机实测，即使不上架也一样）：** App 自己也读不到声音数据库和下载的语音包，下载声音和 Siri 声音是 App 交给苹果自己的语音扩展 MauiAUSP 合成的；我们的扩展连音频组件服务（`AudioComponentRegistrar`、`AudioUnitServer`）都被拒，调不了 MauiAUSP。用私有函数让 App 转交沙盒许可（`sandbox_extension_issue_file` / `_mach`）：语音包路径和这几个服务的许可 App 都开不出来（Operation not permitted）。让 App 代为合成再把声音交给扩展：扩展写不了 App Group、不能联网、连系统通知服务都连不上（`notify_register_check` 返回 9，找不到服务），而且系统给每个调用方单独起一个扩展进程（旁白用的和 App 加载的不是同一个），没有任何通道能把文字交给 App。想要更好的音质，只能在扩展里自带离线引擎。
- `AVSpeechSynthesizer.write()` 的回调**总是投递到主队列**：主线程一被阻塞就永远等不到（Mac 实测）。所以合成在专用线程上等待；`synthesizeSpeechRequest` 若在主线程被调用，等待首块音频时会继续转主线程的 RunLoop。
- 每个声音第一次合成要约 250 ms 加载，之后约 5 ms。扩展在 `allocateRenderResources` 时预热，并在第一句之后空闲时预热对应的外语声音；扩展进程启动后的第一句双语内容仍可能在换声音处卡一下。
- **iOS 26 及更低版本换声音很慢**（iOS 26.5、18.6 模拟器实测）：一句话里换一次声音要 280–330 ms，iOS 27 只要 3–27 ms。以前空闲时单独用副语音读一个字来预热它，合成器就停在了副语音上，下一句主语音要先换回来（多约 290 ms）；预热中途来的请求还得等它读完（约 290 ms）。合起来，预热后的第二句要静音约 600 ms 才出声。现在副语音放在一句主语音的话里预热（`<voice name>`），合成器始终停在主语音上；请求里已经读过副语音就不再单独预热；预热时来了请求就立刻让路。改后两个模拟器上第二句都是 23 ms 出声，换声音降到 32–84 ms（副语音已经加载好了）。iOS 18.6 模拟器上还见过一次：App 加载的扩展收完资源分配后，再也收不到朗读请求（自检那次却正常），原因没查清，可能是模拟器的问题。
- 换声音时苹果要先结束上一段再开始新声音，手机上可能要等一会儿。以前上一段的结尾（最后几十毫秒的字音、余韵、停顿，还有 Sonic 缓冲里的部分）要等新声音开口才放出，播放就会在词尾断掉、过一会儿冒出一小截再读下去，听起来是“停一下、抖两下”。现在空缓冲一到就把整段放出（Sonic 也冲刷干净）；播放端换声音期间多攒一些再开始，真断了也是淡出、攒够再淡入，不会一截一截地放。
- 合成请求走 XPC、渲染走另一条通道，宿主对**下一句**的第一次渲染可能先于扩展收到新请求。渲染块的“完成”标记因此每句只报一次，否则新的一句会被上一句的“完成”直接吞掉（模拟器里复现过）。
- 苹果声音的“静音”不是数字零，而是 2–12（16 位采样值）的底噪，静音判断门限必须高于它，否则结尾空白会被当成声音余韵整段保留。
- 苹果的 SSML：`<voice name="声音标识">` 能在一句里切换声音（`<lang xml:lang>` 也会切到该语言的默认声音）；每段声音结束时 `write()` 都给一个空缓冲，停顿和句子不会，**只有 `didFinish` 才表示整句结束**；切换处保留整段结尾的空白（约 190 ms ÷ 语速）；嵌套的 `<prosody rate>` 是绝对值不是相对值；`prosody volume` 的 dB 刻度不准（-6dB 实测 -12 dB，最多 +5.7 dB），所以音量平衡在采样上做；`rate` 超过 400% 不再变快。
- `pauseSpeaking` 对 `write()` 无效（返回 false），合成没法暂停，只能取消。
- **重启后加倍失效**：手机重启后、第一次解锁之前，App Group 里的文件按系统默认的数据保护是锁着的，可旁白在锁屏界面就已经用上了扩展。扩展读方案失败，用了默认方案（加倍 1 倍、没有规则），还把结果按文件修改时间缓存起来；解锁后文件没变，就一直用缓存，直到在 App 里改一下方案才恢复。现在：读不出来的文件不缓存，下一句再读；共享文件（schemes.json、rules.json、settings.json）写成不加保护（`.noFileProtection`），锁屏时也能读，App 每次打开都会把旧版本写的文件改过来（`SharedStore.openForLockScreen`）。里面只有方案和规则，没有隐私。
- **Apple 芯片的 Mac 上**（macOS 27，TestFlight 装的 iPhone 版）：旁白能用旁白助手，速度正常。Mac 上的扩展能用的声音和 iPhone 不同：婷婷、Samantha 是精简版（`compact`），没有 iPhone 的内置版（`super-compact`），默认方案里的内置版标识会退回这种语言的默认声音（即精简版婷婷）；另外还有 Eloquence 系列，没有 Siri 和高音质声音。调试签名的扩展在 Mac 上启动不了（launchd 报 163，Security policy issue），必须通过 TestFlight 或 App Store 安装才能测；Mac 的命令行程序也找不到任何 `ausp` 组件，没法像在 iPhone 上那样用 `-latency` 直接驱动。开发参数（`-autotest`、`-latency`、`-listVoices`）的输出是逐行写出的，在 Mac 上跑完会自己退出，可以用 `open --stdout <文件> /Applications/旁白助手.app --args -listVoices` 看结果。
- 语音扩展在真机上不能往 App Group 写任何东西（文件和 group 的 UserDefaults 都不行），要量只能看日志；设置一律由 App 写成 JSON 文件，扩展只读（`UserDefaults(suiteName:)` 跨进程不可靠）。
